# PRD: Docmost → OpenViking Sync

## 1. Назначение

`docmost-openviking-sync` поддерживает актуальную поисковую копию выбранных
пространств Docmost в OpenViking. Docmost остаётся единственным источником
правды: сервис читает его страницы и не изменяет их.

Результат — агент OpenViking может находить и читать содержание документации
Docmost как resources, включая контекст пространства и положение страницы в
дереве.

## 2. Цели V1

- Синхронизировать много пространств Docmost в один заданный корень resources
  OpenViking.
- По умолчанию синхронизировать все доступные вызывающему сервису spaces.
- Позволять сузить набор пространств allowlist и исключить его denylist.
- Предоставить ручной запуск синхронизации.
- Предоставить постоянно работающий демон на Go, который автоматически
  выполняет синхронизацию по настраиваемому интервалу.
- Делать повторный запуск безопасным и инкрементальным: неизменённые страницы
  не должны переписываться или переиндексироваться без необходимости.
- Корректно отражать создание, изменение, переименование, перемещение и
  удаление страниц.

## 3. Не-цели V1

- Синхронизация вложений и файлов, прикреплённых к страницам.
- Перенос или интерпретация ACL, групп и прав доступа Docmost.
- Двусторонняя синхронизация или запись в Docmost.
- Создание public shares в Docmost.

## 4. Пользователи и сценарии

### Администратор документации

Подключает Docmost и OpenViking, при необходимости задаёт allowlist/denylist
spaces и запускает первичную синхронизацию. После этого демон поддерживает
индекс в актуальном состоянии.

### Агент OpenViking

Ищет техническую или рабочую документацию. Поиск возвращает ресурс, из
которого можно прочитать актуальный текст страницы, её исходный URL, space и
хлебные крошки.

### Оператор

Запускает разовую синхронизацию перед диагностикой или после изменения
конфигурации, получает машиночитаемый результат и ненулевой код при ошибке.

## 5. Функциональные требования

### 5.1 Отбор spaces

1. Сервис получает список доступных spaces через Docmost API.
2. При пустых фильтрах в синхронизацию входят все spaces.
3. Allowlist ограничивает набор указанными стабильными идентификаторами или
   slug spaces.
4. Denylist исключает spaces из результата; при конфликте denylist имеет
   приоритет.
5. В итоговом отчёте указываются включённые, исключённые и недоступные spaces.

### 5.2 Представление страниц

1. Каждая страница сохраняется отдельным Markdown-ресурсом OpenViking.
2. Идентичность ресурса строится на неизменяемом `page_id`, а не на заголовке
   или положении в дереве.
3. Содержимое включает нормализованный Markdown страницы и метаданные:
   `docmost_page_id`, `space_id`, `space_slug`, title, canonical URL,
   breadcrumb/path и время последнего изменения в Docmost.
4. Перемещение или переименование обновляет метаданные и текст без создания
   второй копии страницы.
5. Ссылки между страницами по возможности сохраняются в пригодном для чтения
   виде.

### 5.3 Сверка состояния

1. Перед записью сервис определяет, изменилась ли исходная страница с прошлого
   успешного запуска, по версии/времени изменения Docmost и хэшу нормализованного
   содержимого.
2. Изменённые и новые страницы записываются в OpenViking и индексируются.
3. Неизменённые страницы пропускаются.
4. Страница, исчезнувшая из разрешённого набора Docmost, удаляется из
   управляемого этим сервисом корня OpenViking.
5. Сервис не изменяет ресурсы за пределами своего корня.
6. После прерванного запуска следующий запуск завершает сверку без ручной
   очистки и без дублирования ресурсов.

### 5.4 Режимы работы

Сервис поставляется одним Go-бинарником с двумя режимами:

- `sync` — единоразовая синхронизация и завершение процесса;
- `daemon` — цикл синхронизации с настраиваемым интервалом и немедленной
  первой попыткой после запуска.

Оба режима используют одинаковую конфигурацию и один алгоритм сверки.

В режиме `daemon` сервис принимает HMAC-подписанные page events Docmost,
объединяет серию быстрых изменений и запускает сверку. Интервальная полная
сверка сохраняется как механизм восстановления после потерянных событий.

### 5.5 Наблюдаемость

Каждый запуск формирует структурированный итог: длительность, обработанные
spaces, количество созданных/обновлённых/пропущенных/удалённых страниц и
ошибки. Логи должны позволять определить страницу и space, на которых возникла
ошибка, не раскрывая учётные данные.

Ошибка одной страницы не должна препятствовать обработке остальных страниц;
запуск считается неуспешным, если есть хотя бы одна необработанная ошибка.

## 6. Конфигурация V1

Конфигурация определяет адреса Docmost и OpenViking, параметры аутентификации,
целевой корень OpenViking, интервал демона, allowlist и denylist spaces, а
также параметры webhook receiver. Каждый параметр можно задать через JSON,
ENV или CLI; приоритет: CLI > ENV > JSON > defaults. Файл конфигурации
необязателен, чтобы сервис можно было запускать как контейнер только с ENV.
Секреты в Kubernetes передаются через Secret/ENV, а не через JSON-файл.

Значения по умолчанию:

| Параметр | Значение |
| --- | --- |
| Набор spaces | все доступные |
| Allowlist / denylist | пустые |
| Режим по умолчанию | `sync` |
| OpenViking URL | `http://127.0.0.1:1933` |
| OpenViking root | `viking://user/resources/docmost` |
| Первый запуск демона | сразу после старта |
| Полная сверка | раз в сутки |
| Webhook debounce | 10 секунд |

## 7. Критерии приёмки V1

1. На тестовом Docmost с минимум тремя spaces пустая конфигурация переносит
   страницы всех трёх spaces.
2. Allowlist оставляет только указанные spaces; denylist исключает space даже
   при его наличии в allowlist.
3. Повторный `sync` без изменений не записывает страницы повторно.
4. Правка, перемещение и переименование страницы обновляют единственный
   соответствующий resource.
5. Удаление страницы из Docmost удаляет её из управляемого корня OpenViking.
6. `daemon` выполняет синхронизацию сразу и затем не раньше заданного интервала.
7. Ошибка одной страницы отражается в отчёте, не останавливая обработку других.

## 8. Следующий этап

После V1 планируются:

1. Синхронизация вложений с привязкой к исходной странице.
2. Отображение ACL Docmost в модель доступа OpenViking.

Каждое из направлений требует отдельного дизайна: вложения влияют на объём и
форматы индексации, ACL — на модель идентичностей и безопасность доступа.
